## Summary
This change implements Spec 0005: visual canvas inspector, Vite source location tagging, in-browser recast AST class/text modifications, right-docked inspector panel, and PostgreSQL snapshot auto-persistence. The architecture, postMessage contracts, and AST formatting preservation are cleanly structured, but two critical correctness bugs block merge: a naive regex string transformer in the Vite inspector plugin that corrupts TypeScript generics and crashes the preview compiler, and a debounced VFS write race that drops writes during rapid multi-file visual edits. Several major issues around missing instant styles in the UI, input-focus undo interception, line-only AST matching, and missing path traversal validation in the snapshot API also require resolution.

## Blockers

### 🔴 Injected Vite transform plugin corrupts TypeScript generics and comparisons, crashing the preview Vite compiler, `packages/sandbox/src/template.ts:72`
**Problem**: In `STARTER_TEMPLATE_FILES["plugins/spark-inspector.js"]`, the string transform scans for `ch === "<" && /[a-zA-Z]/.test(next)`. This matches any identifier preceded by `<` outside string literals and line comments. When parsing TypeScript or TSX code containing generics such as `useState<boolean>()`, `Array<string>`, `Promise<void>`, or even the starter template's own `useState<string>("Initializing PGlite...")` (`packages/sandbox/src/template.ts:487`), the regex matches `<boolean` or `<string` and injects `data-source-loc`, transforming it into `useState<boolean data-source-loc="src/App.tsx:1:34">(false)`. Similarly, expressions like `a <b` are transformed into `a <b data-source-loc="...">`.
**Why it matters**: In Vite, esbuild throws an immediate syntax error (`Expected ">" but found "data-source-loc"`) when compiling any `.tsx` file that uses TypeScript generics. Because the starter template itself contains `useState<string>(...)`, the preview application fails to compile and crashes on boot in the WebContainer sandbox.
**Suggested fix**: Replace the naive string scanner with a proper Babel AST transform or configure `@vitejs/plugin-react` with Babel plugins (e.g. `@babel/plugin-transform-react-jsx-source` or an AST visitor targeting `JSXOpeningElement`) in `vite.config.ts`, ensuring that `TypeParameterInstantiation` and binary comparison expressions are never treated as JSX tags.

### 🔴 Rapid visual edits cause data loss in virtual filesystem writes due to timer overwrite, `apps/web/src/hooks/useProjectFiles.ts:143`
**Problem**: In `updateFileContent`, virtual filesystem updates are debounced by 300ms using a single timer ref:
```typescript
if (debouncedWriteTimeoutRef.current) {
  clearTimeout(debouncedWriteTimeoutRef.current);
}
debouncedWriteTimeoutRef.current = setTimeout(() => {
  onWriteFiles?.([{ path: filePath, content: newContent }]);
}, 300);
```
If a user edits an element in `src/App.tsx` and then selects and edits an element in `src/Card.tsx` within 300ms, `clearTimeout` cancels the write for `src/App.tsx`. The new timer closure only contains `src/Card.tsx`.
**Why it matters**: `src/App.tsx` is permanently omitted from the write sent to the WebContainer virtual filesystem, leaving the live preview in an out-of-sync, stale state while the client store claims the file was updated.
**Suggested fix**: Maintain a `pendingWritesRef = useRef<Map<string, string>>(new Map())` that accumulates all modified file paths and contents. When the debounced timer fires, convert all entries in `pendingWritesRef` into the `ProjectFile[]` array passed to `onWriteFiles`, and clear the map.

## Major

### 🟠 `InspectorPanel` never computes or passes `instantStyles`, breaking zero-latency preview updates (AC-5), `apps/web/src/components/inspector/InspectorPanel.tsx:86`
**Problem**: Acceptance criterion AC-5 requires: "Changing visual controls immediately updates element styles in the preview DOM via `PREVIEW_INJECT_STYLES` for zero latency feedback...". While `useProjectFiles.ts` supports `instantStyles`, `InspectorPanel.tsx`'s `handleClassToggle` helper only passes `{ newClasses: [newClass], removeClasses: toRemove }`. It never computes or passes `instantStyles` for color presets, typography, padding, margins, or borders.
**Why it matters**: Zero-latency DOM style injection is completely inactive in the UI. Users experience the full 300ms debounce delay plus WebContainer write and Vite HMR rebuild times on every button click before seeing visual feedback in the canvas.
**Suggested fix**: Update `handleClassToggle` to accept and pass the corresponding inline CSS style in `onApplyStyle` (e.g. for color presets pass `instantStyles: { backgroundColor: color }`, for text color pass `instantStyles: { color }`, for padding pass `instantStyles: { padding: ... }`), allowing instant DOM styling before the AST write completes.

### 🟠 Global `Command+Z` handler intercepts native undo while editing Inspector text input, `apps/web/src/app/page.tsx:138`
**Problem**: The global `keydown` listener in `BuilderPage` checks:
```typescript
if (isTextInput && !active.closest("[aria-label='Visual Canvas Inspector Panel']")) {
  return;
}
```
When a user is actively typing in the text input inside the Inspector Panel (`#inspector-element-text-input`), `!active.closest(...)` evaluates to false, so the function does not return. Instead, it runs `e.preventDefault()` and calls `undo()`.
**Why it matters**: Creators trying to undo a typo in the text input have their native keystroke undo blocked, and previous project files/canvas edits are reverted unexpectedly.
**Suggested fix**: Replace the check with `if (isTextInput) return;` uniformly so that all focused text inputs retain native undo/redo behavior without triggering project-level canvas history reversions.

### 🟠 `ast-modifier` matches JSX elements by line number alone, corrupting adjacent elements on the same line, `apps/web/src/lib/ast-modifier.ts:58`
**Problem**: In both `updateElementClasses` (line 58) and `updateElementText` (line 154), AST traversal matches an element with `if (options.source?.line && line !== options.source.line)`. It ignores `options.source.column` and tag name. When multiple JSX elements are on the same line (e.g. `<div><button>Edit</button><button>Delete</button></div>`), `updateElementClasses` always matches and alters the first element on the line. In `updateElementText`, if a parent and child share a line (e.g. `<h1><span>Title</span></h1>`), the parent is matched, and because the parent has element children, it fails with "Element contains dynamic JSX expressions or child elements".
**Why it matters**: Selecting an element on a shared line applies Tailwind classes to the wrong element or falsely rejects valid static text editing.
**Suggested fix**: Match candidate JSX elements using both `line` and `column` (e.g. match the closest column <= `options.source.column`), and optionally verify that the AST node's tag name matches the selected element's tag name.

### 🟠 Path traversal tokens are not validated in snapshot persistence endpoint, `apps/web/src/app/api/projects/[id]/snapshots/route.ts:11`
**Problem**: Spec 0005 states: "Source file writes are restricted to relative paths within the project workspace, rejecting any path containing directory traversal tokens (such as `../`)." However, `createSnapshotSchema` only validates that keys are strings without checking for `..` or path traversal characters. `filterSourceFiles` also does not sanitize traversal tokens.
**Why it matters**: Clients could submit snapshot maps containing keys like `../../package.json` or directory escape sequences that corrupt virtual filesystem extraction in WebContainer runners or break tree hash computation.
**Suggested fix**: Add a refine check or regex validation in `createSnapshotSchema` or in `filterSourceFiles` ensuring every path is relative and does not contain `..` or leading slashes.

## Minor

### 🟡 Internal database error details are leaked in 500 responses, `apps/web/src/app/api/projects/[id]/snapshots/route.ts:81`
**Problem**: In the catch block of `POST /api/projects/[id]/snapshots`, the handler returns `{ error: "Failed to persist snapshot", message: errorObj.message }` with status 500.
**Why it matters**: Unsanitized error messages from the database layer can expose schema structure, table names, or connection pool parameters to clients.
**Suggested fix**: Log `errorObj` to the server logger and return a generic error message (e.g. `{ error: "Internal server error" }`) in the HTTP response.

### 🟡 Empty string text updates are dropped in `page.tsx`, `apps/web/src/app/page.tsx:64`
**Problem**: In the `PREVIEW_UPDATE_TEXT` bridge message handler:
```typescript
const payload = msg.payload as { text?: string };
if (payload?.text) {
  applyTextUpdate(payload.text);
}
```
If `payload.text` is `""` (empty string, e.g. user deletes all text and presses enter), `payload?.text` is falsy, so `applyTextUpdate` is never called.
**Why it matters**: Users cannot clear text or set it to an empty string via inline editing.
**Suggested fix**: Check `if (typeof payload?.text === "string")` instead of `if (payload?.text)`.

### 🟡 Missing unmount cleanup for auto-save and debounce timers in `useProjectFiles`, `apps/web/src/hooks/useProjectFiles.ts:45`
**Problem**: `debouncedWriteTimeoutRef` and `autoSaveTimeoutRef` are not cancelled when the `useProjectFiles` hook unmounts.
**Why it matters**: If a user navigates away within 3 seconds of making a style change, the timers may fire against an unmounted component or attempt to post messages to an unmounted preview iframe.
**Suggested fix**: Add a cleanup `useEffect` returning `() => { if (debouncedWriteTimeoutRef.current) clearTimeout(...); if (autoSaveTimeoutRef.current) clearTimeout(...); }`.

### 🟡 `@babel/parser` is declared in `devDependencies` instead of `dependencies`, `apps/web/package.json:37`
**Problem**: `apps/web/src/lib/ast-modifier.ts` directly imports `@babel/parser` at runtime in the browser client bundle. `@babel/parser` is listed in `devDependencies` rather than `dependencies`.
**Why it matters**: In production deployment environments running `pnpm install --prod`, devDependencies are omitted, which can cause module resolution failures.
**Suggested fix**: Move `@babel/parser` from `devDependencies` to `dependencies` in `apps/web/package.json`.

### 🟡 Untrusted postMessage source verification in `SandboxRunnerPage`, `apps/web/src/app/sandbox/runner/page.tsx:106`
**Problem**: `SandboxRunnerPage` handles messages with `isFromParent = event.source === window.parent`. If false, it forwards messages upstream to `window.parent` without validating that `event.source === iframe?.contentWindow`. In addition, `postMessage` calls use wildcard target origin `*`.
**Why it matters**: Any window or popup with a reference to the sandbox runner can inject fake bridge events (such as spoofed element selections or navigations) into the host workbench.
**Suggested fix**: Validate that non-parent messages originate specifically from `iframeRef.current?.contentWindow` and restrict `postMessage` target origin to `targetOrigin`.

## Strengths
- **Clean separation of concerns**: Excellent architecture decoupling DOM inspection in the runner from AST transformation in the host workbench via strictly typed postMessage contracts in `@spark/shared`.
- **Formatting preservation**: Using `recast` with Babel parser for AST manipulation successfully preserves comments, imports, and indentation in source files, avoiding git diff pollution.
- **Security design in AST modifier**: `isWorkspaceFilePath` rigorously enforces path boundaries, preventing AST modification on external packages or path traversal attempts.
- **Accessible multi-viewport layout**: Accessible workbench supporting desktop resizable panels and mobile bottom navigation with proper WCAG labels and landmark semantics.

## Test coverage
The test signal is `configured`. Unit tests exist for components, hooks, AST modifier, and snapshot route, and all 160 Vitest tests pass. However, there are significant coverage gaps masking critical bugs:
1. `template.test.ts` only asserts that the string key `"plugins/spark-inspector.js"` exists in `STARTER_TEMPLATE_FILES`; it never executes `sparkInspector().transform` against TSX fixtures, allowing the TypeScript generic corruption blocker to go undetected.
2. `useProjectFiles.test.ts` tests `applyStyleUpdate` with mock `instantStyles`, but `InspectorPanel.test.tsx` never tests that clicking color/spacing buttons produces `instantStyles`.
3. `page.test.tsx`'s Cmd+Z test triggers keydown without verifying that focused text inputs in the inspector panel retain native undo.
