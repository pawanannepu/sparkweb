## Summary

Slice 7 implements multi modal design extraction and outline guided code generation across `@spark/shared`, `@spark/db`, and `apps/web`, adding `supportsVision` model metadata, `design_attachments` and `design_outlines` schemas with a 60 second thread extraction lease, `sharp` image normalization backed by `ArtifactStore`, SSRF guarded `cheerio` URL inspection, editable `DesignOutlineCard` drafts, and atomic Stage 2 prompt injection in `POST /api/projects/[id]/generate` plus AC-10 attachment cleanup. Workspace TypeScript checks (`5` packages), Biome lint (`278` files), and Vitest (`85` test files, `497` tests) all pass, with thorough PGlite transactional tests for schemas, leases, and cascade deletion. However, four major issues should be fixed before merge: unconfigured OpenRouter models hide the missing vision key prompt in `PromptComposer`, cold server caches reject `openrouter/free` and live OpenRouter vision models with `VISION_MODEL_REQUIRED`, `handleBuildOutline` and `DesignOutlineCard` can revert a locked outline or drop unsaved edits, and `defaultPinnedUrlTransport` has zero test coverage while letting malformed redirects and socket resets surface as `500`.

## Major

### 🟠 Unconfigured provider fallback hides `"Add a vision provider key"` in vision warning banner, `apps/web/src/components/generation/PromptComposer.tsx:151`
**Problem**: In `PromptComposer` (`apps/web/src/components/generation/PromptComposer.tsx:151-154`), `visibleOpenRouterModels` falls back to returning all `openRouterModels` whenever `configuredProviders` is empty (`[]`), and `configuredVisionModels` (`lines 182-185`) filters `visibleOpenRouterModels` alongside `configuredDirectModels`. When `useAiSettings` passes `configuredProviders = []` (the default state before any API key is saved) and a user attaches an image while a non vision model is active, `configuredVisionModels.length > 0` evaluates to `true`.
**Why it matters**: Instead of rendering the `"Add a vision provider key"` button required by AC-3 when no vision provider is configured, the banner displays `"Switch to ..."` buttons for unconfigured OpenRouter models, causing extraction to fail on submit with `PROVIDER_KEY_MISSING`.
**Suggested fix**: Separate the browsable dropdown list from `configuredVisionModels` so OpenRouter models are included in `configuredVisionModels` only when `configuredProviders?.includes("openrouter")` is true.

### 🟠 Cold worker cache rejects `openrouter/free` and live OpenRouter vision models with `VISION_MODEL_REQUIRED`, `apps/web/src/app/api/projects/[id]/outlines/route.ts:51`
**Problem**: `resolveCachedModelVisionCapability` (`apps/web/src/app/api/projects/[id]/outlines/route.ts:51-69`) checks `OPENROUTER_DEFAULT_MODELS`, `DIRECT_MODELS`, the in memory `getOpenRouterModelsCacheMap()` and `getProviderModelsCacheMap()`, and finally `isDirectModelVisionCapable`. However, `OPENROUTER_DEFAULT_MODELS` (`packages/shared/src/ai-models.ts:67-169`) omits `"openrouter/free"` (auto selected as the default OpenRouter model in `apps/web/src/hooks/useAiSettings.ts:46`) and live OpenRouter catalog models such as `"openai/gpt-4.1"`. Meanwhile, `PromptComposer` treats any model returned by `/api/ai/models` as a known model (`isCustomModelId === false`), so it does not render the `visionOverride` toggle.
**Why it matters**: Whenever `POST /api/projects/[id]/outlines` hits a fresh serverless worker or a process restarted after the client loaded `/api/ai/models`, the cache map is empty and `POST /outlines` rejects valid vision models with `400` (`VISION_MODEL_REQUIRED`), leaving the creator with no `visionOverride` escape hatch.
**Suggested fix**: When `resolveCachedModelVisionCapability` misses the static lists and in memory cache for an OpenRouter model (or other dynamic catalog model), fetch the model metadata via `fetchOpenRouterModelsForKey` before returning `false` (or fall back only when the live catalog lookup also fails or reports `supportsVision: false`).

### 🟠 `handleBuildOutline` reverts locked outlines on stream abort/error and `DesignOutlineCard` drops unsaved edits, `apps/web/src/app/page.tsx:507`
**Problem**: `handleBuildOutline` (`apps/web/src/app/page.tsx:507-528`) optimistically sets the outline to `"confirmed"`, calls `submitBuildFromOutline`, and runs `if (!started) setOutlines(previousOutlines)`. In `useGenerationLoop` (`apps/web/src/hooks/useGenerationLoop.ts:753-761`), cancelling via Stop (`AbortError`) or encountering a stream read error after `POST /generate` returned `200` returns `false`, even though `startOutlineBuildTransaction` (`packages/db/src/multimodal-queries.ts:637-730`) already committed `status = "confirmed"` in PostgreSQL. On pre lock failures (such as `400 PROVIDER_KEY_MISSING`), restoring `previousOutlines` triggers `DesignOutlineCard`'s `useEffect` (`apps/web/src/components/generation/DesignOutlineCard.tsx:61-63`), overwriting `draft` with stale `previousOutlines` data and discarding edits whose 500ms `PATCH` debounce timer was cancelled in `handleBuildClick` (`DesignOutlineCard.tsx:145-149`). Separately, `useEffect([outline])` runs whenever any `PATCH` response updates `outline` in `page.tsx`, overwriting text typed while that `PATCH` HTTP request was in flight, and `DesignOutlineCard` never clears `debounceTimerRef` when `outline.status` transitions to `"superseded"`.
**Why it matters**: Stopping or losing connection during an outline build reverts the UI card to editable `"ready"` state so subsequent edits and builds fail with `409`; failing before locking erases unsaved user tweaks; and typing during a `PATCH` round trip loses keystrokes.
**Suggested fix**: Distinguish pre lock request failures from post lock stream errors or aborts in `submitBuildFromOutline` (keeping `"confirmed"` once `200` SSE streaming starts or on `409`, and keeping `latestPayload` in client state on pre lock `400` retries), sync `draft` in `DesignOutlineCard` only on outline ID changes, status transitions, or explicit resets while ignoring stale `PATCH` responses when a newer edit is pending, and clear `debounceTimerRef` whenever `outline.status !== "ready"`.

### 🟠 Untested `defaultPinnedUrlTransport` and unhandled redirect/socket errors leak `500` on external URLs, `apps/web/src/lib/multimodal/url-extractor.ts:291`
**Problem**: Every test in `apps/web/src/lib/multimodal/url-extractor.test.ts` injects mock `transport` and `dnsLookup` stubs, leaving all 125 lines of `defaultPinnedUrlTransport` (`apps/web/src/lib/multimodal/url-extractor.ts:291-416`, including IP pinned `lookup`, SNI `servername`, timeout aborts, and streaming `maxBytes` enforcement) and `defaultDnsLookup` (`lines 222-237`) with zero test execution. Inside that untested path, `fetchWithRedirects` (`line 476`) calls `new URL(location, parsed)` without a `try/catch`, and `defaultPinnedUrlTransport` (`lines 381-384`) rejects raw `res.on("error")` events instead of wrapping them in `UrlExtractionError`.
**Why it matters**: Under `TEST_SIGNAL = configured`, security critical network pinning and byte limit code is unverified by tests, and untrusted target servers returning a malformed `Location` redirect header or resetting the response stream trigger HTTP `500` responses in `POST /outlines` instead of structured `502` (`URL_FETCH_FAILED`) recovery guidance.
**Suggested fix**: Wrap `new URL(location, parsed)` in a `try/catch` and convert `res.on("error")` socket failures into `UrlExtractionError("URL_FETCH_FAILED", 502, ...)`, and add tests exercising `defaultPinnedUrlTransport` against a local `http` server (covering IP pinned `lookup`, `maxBytes` `URL_TOO_LARGE` abort, `timeoutMs` `URL_TIMEOUT` abort, malformed redirect `Location`, and response stream error mapping).

## Minor

### 🟡 Model JSON/schema parse failures return `500` and leak raw exception messages, `apps/web/src/lib/multimodal/outline-extractor.ts:230`
**Problem**: `parseOutlineJson` (`apps/web/src/lib/multimodal/outline-extractor.ts:28-49`) and `DesignOutlinePayloadSchema.safeParse` failure (`lines 231-236`) throw generic `Error` instances rather than a structured `422` error using `OUTLINE_INVALID_PAYLOAD` (already declared in `packages/shared/src/multimodal.ts:145` but unused). Additionally, `handleMultimodalRouteError` (`apps/web/src/lib/multimodal/serializers.ts:78-79`) returns raw `err.message` strings in `500` responses.
**Why it matters**: Malformed model JSON outputs surface as HTTP `500` errors instead of actionable `422` `OUTLINE_INVALID_PAYLOAD` retries, and unexpected storage or SQL errors expose internal details to clients.
**Suggested fix**: Throw a structured `422` error carrying `OUTLINE_INVALID_PAYLOAD` from `outline-extractor.ts`, map it in `outlines/route.ts`, and return the generic `fallbackMessage` instead of raw `err.message` on `500` responses in `handleMultimodalRouteError`.

### 🟡 DB concurrency gaps across thread creation, lease release, cloning, and outline build locks, `packages/db/src/multimodal-queries.ts:60`
**Problem**: Four narrow concurrency issues exist in `packages/db/src/multimodal-queries.ts`: (1) `resolveOrCreateProjectThread` (`lines 60-83`) selects and inserts `"Main thread"` without locking the owning `projects` row (`FOR UPDATE`), so concurrent `GET /threads/default/state` and `POST /attachments` calls on a brand new project can create two default threads and misroute pending uploads (`422` on extraction); (2) `releaseOutlineExtractionLease` (`lines 330-341`) clears `outlineLockExpiresAt = null` unconditionally, allowing a slow extraction past 60 seconds to clear a newer request's active lease in `finally`; (3) `cloneDesignOutline` (`lines 573-635`) supersedes `ready` rows and computes `maxSeq + 1` without locking `prompt_threads` (`FOR UPDATE`) or enforcing one `ready` outline per thread via a partial unique index; and (4) `startOutlineBuildTransaction` (`lines 637-730`) checks `checkActiveGeneration` with a plain `SELECT` without `FOR UPDATE` locking.
**Why it matters**: Concurrent clicks or multi tab actions on fresh projects or slow extractions can produce duplicate threads, `23505` sequence collisions (`500`), or prematurely cleared leases.
**Suggested fix**: Lock the `projects` row (`FOR UPDATE`) when creating a default thread in `resolveOrCreateProjectThread`, lock the `prompt_threads` row (`FOR UPDATE`) inside `cloneDesignOutline` and `startOutlineBuildTransaction`, and make `releaseOutlineExtractionLease` match the acquired `expiresAt` timestamp.

### 🟡 SSRF edge hardening for trailing dot localhost, `::/96`, and exhausted byte budgets, `apps/web/src/lib/multimodal/url-extractor.ts:200`
**Problem**: `validatePublicHttpUrl` (`apps/web/src/lib/multimodal/url-extractor.ts:200-208`) checks `hostname === "localhost" || hostname.endsWith(".localhost")` without stripping trailing dots (so `http://localhost./` slips through to DNS lookup), and `isBlockedIp` (`lines 140-151`) covers every CIDR named in AC-5 (`::`, `::1`, `::ffff:0:0/96`, `fe80::/10`, `fc00::/7`, `ff00::/8`) but omits deprecated IPv4 compatible IPv6 (`::/96`, such as `::127.0.0.1`) and NAT64 (`64:ff9b::/96`). Also in `fetchWithRedirects` (`line 447`), `Math.max(1, params.remainingBytes - bytesUsed)` allows a 1 byte fetch when `remainingBytes <= bytesUsed`, and `res.on("data")` (`line 353`) aborts `controller` without calling `res.destroy()`.
**Why it matters**: Malformed or adversarial URLs such as `http://localhost./` or `http://[::127.0.0.1]/` are rejected later or inconsistently (`502` vs `422`), and oversized streams can queue extra chunks before socket teardown.
**Suggested fix**: Normalize trailing dots on `hostname` before the `localhost` check, block `::/96` and `64:ff9b::/96` in `isBlockedIp`, throw `URL_TOO_LARGE` immediately when `remainingBytes - bytesUsed <= 0`, and call `res.destroy()` when `totalBytes > req.maxBytes`.

### 🟡 Synchronous stale sweep stalls uploads and attachment `DELETE` deletes DB rows before S3 blobs, `apps/web/src/lib/multimodal/cleanup.ts:30`
**Problem**: `POST /api/projects/[id]/attachments` (`apps/web/src/app/api/projects/[id]/attachments/route.ts:85`) awaits `sweepStalePendingAttachments()` before sending `201`, and `cleanup.ts:31-47` loops sequentially through up to 25 objects one by one. In `DELETE /api/projects/[id]/attachments/[attachmentId]` (`apps/web/src/app/api/projects/[id]/attachments/[attachmentId]/route.ts:72-86`), the DB row is deleted first and then `artifactStore.deleteObject` runs; if S3 deletion transiently throws, the client receives `500` (keeping the deleted image in `PromptComposer`) while the DB row is already gone and unreachable by future sweeps.
**Why it matters**: With S3/R2 configured, 25 sequential `DELETE` requests add noticeable latency to image uploads, and transient S3 failures during attachment removal desynchronize UI state from PostgreSQL and leave orphaned blobs.
**Suggested fix**: Run stale cleanup deletions with bounded concurrency (`Promise.allSettled`) or via Next.js `after()`, and in `DELETE /attachments/[attachmentId]` log or retry transient blob deletion errors rather than returning `500` after the DB row has been removed.

### 🟡 Missing tests on `outlines/route.ts` error branches, `cloneDesignOutline` superseding, pixel bomb guard, and UI input edges, `apps/web/src/app/api/projects/[id]/outlines/route.test.ts:92`
**Problem**: Several new branches lack test coverage under `TEST_SIGNAL = configured`: `outlines/route.test.ts` never tests `PROVIDER_KEY_MISSING` (`outlines/route.ts:146-155`), missing storage object `404` (`lines 186-191`), cache hit lookup (`lines 58-66`), or invalid UUID inputs (`lines 79-81`, `105-116`); `multimodal-queries.test.ts` never tests `cloneDesignOutline` superseding an existing `ready` outline (`multimodal-queries.ts:580-586`); and `image-pipeline.test.ts` omits the `limitInputPixels` error branch (`image-pipeline.ts:123`). On the UI side, `DesignOutlineCard.tsx:546` only checks `enabledSectionsCount === 0` before enabling `Build App` instead of validating `DesignOutlinePayloadSchema` (for example invalid hex codes or empty `appSummary`), and `PromptComposer.tsx:202` ignores active `uploadingCount` when checking the 4 image slot cap.
**Why it matters**: Regressions in key gating, storage `404` handling, or `/clone` superseding transitions can slip past unit tests, and invalid inline edits trigger failing `POST /generate` requests.
**Suggested fix**: Add test cases for `PROVIDER_KEY_MISSING`, missing storage blob `404`, cache hits, invalid UUIDs, `cloneDesignOutline` superseding a prior `ready` draft, and `limitInputPixels` rejection; validate `DesignOutlinePayloadSchema` before allowing `Build App` and count in flight uploads against `MAX_DESIGN_IMAGES`.
