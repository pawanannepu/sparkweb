# Review, main, 2026-11-24

**Reviewed by**: Gemini Pro (author on Gemini Flash)
**Scope**: 23 files, uncommitted
**Verdict**: Blocked

## Summary
This change implements the self healing verification engine from Spec 0006, adding diagnostic parsing, bridge health handshakes, a server repair endpoint, deferred snapshot persistence, and progress UI cards. The test suites pass cleanly, and the diagnostic classification and fingerprint logic are well designed. Two blocking security and correctness issues require attention before merge: prompt messages can be updated without project ownership checks, and manual repair passes fail on unpersisted message identifiers.

## Blockers
### 🔴 Missing project ownership check on message updates, `apps/web/src/app/api/projects/[id]/snapshots/route.ts:96`
**Problem**: The snapshot endpoint accepts an arbitrary `messageId` and updates the `promptMessages` record without verifying that the message belongs to a thread inside the authenticated user's project. The repair endpoint in `apps/web/src/app/api/projects/[id]/repair/route.ts:110` similarly checks that `messageId` exists, but does not confirm it belongs to the target project.
**Why it matters**: A user who authenticates on their own project could submit the message identifier of another user's project. The endpoint would overwrite the status, tool calls, and snapshot pointer of that foreign prompt message in production.
**Suggested fix**: You can join `promptMessages` with `promptThreads` in the query to verify that `promptThreads.projectId` matches the route `projectId`, or use an explicit ownership check before performing the update.

### 🔴 Manual repair fails on unpersisted message identifiers, `apps/web/src/hooks/useGenerationLoop.ts:445`
**Problem**: When manual repair runs without a prior generation message in memory, `triggerRepair` creates a synthetic identifier string starting with `repair-`. The repair endpoint queries the database for this identifier using `where(eq(promptMessages.id, messageId))`. This lookup fails with a database UUID parsing error or a 404 response. When a previous message identifier is present, it overwrites that earlier message rather than creating a new record.
**Why it matters**: Clicking the manual repair button on the error banner after page reload or outside an active generation session will always fail. Furthermore, reusing prior message identifiers corrupts earlier conversation history.
**Suggested fix**: You can create a real assistant message row in the database when initiating manual repair, as required by acceptance criterion 8, and pass that valid message UUID to the repair route.

## Major
### 🟠 Unresponsive runner treated as healthy on timeout, `apps/web/src/hooks/usePreviewBridge.ts:68`
**Problem**: When the preview runner drops a bridge message, crashes, or becomes unresponsive, the safety timeout in `usePreviewBridge` resolves with `{ healthy: true }`.
**Why it matters**: A completely frozen or crashed preview runner is reported as healthy once the timeout window elapses. The application will then commit an unverified broken state to PostgreSQL as a clean snapshot.
**Suggested fix**: You can have the fallback safety timeout resolve with `{ healthy: false }` and an explanatory error message, or trigger a sandbox restart when the runner fails to answer the health check.

### 🟠 Cancellation does not abort active self healing loop, `apps/web/src/hooks/useGenerationLoop.ts:320`
**Problem**: When a user cancels generation, `cancelGeneration` aborts the primary generation controller. The repair loop in `runSelfHealingVerificationLoop` does not pass an abort signal to the repair endpoint and does not check whether generation was cancelled.
**Why it matters**: The background loop continues sending repair requests and applying patches after the user clicked stop. Once finished, it can commit an unexpected snapshot.
**Suggested fix**: You can share the abort controller signal with the repair fetch call and check `controller.signal.aborted` at the start of each iteration in the while loop.

### 🟠 Lost update event causes four second delay on every repair, `apps/web/src/app/sandbox/runner/page.tsx:183`
**Problem**: When file patches stream in, the runner applies them immediately. Hot module replacement often finishes before the repair stream closes and before `PREVIEW_HEALTH_CHECK` arrives. Because `SandboxRunnerPage` only inspects health checks that are already pending when the replacement event arrives, the event is ignored and the health check waits for the full four second fallback timer.
**Why it matters**: Every repair attempt incurs a four second delay even when the application compiled cleanly in fifty milliseconds.
**Suggested fix**: You can store a timestamp of the most recent successful hot module update, and resolve the health check immediately if an update succeeded recently and no errors are present.

### 🟠 Retry button disabled after failed generation turn, `apps/web/src/app/page.tsx:316`
**Problem**: The builder page calculates remaining retries as `Math.max(0, 3 - healingTelemetry.totalRepairs)`. When generation exhausts its three repair attempts, remaining retries becomes zero.
**Why it matters**: The repair button on the preview error banner becomes disabled. Creators are prevented from triggering an on demand repair pass with a fresh three attempt budget as specified in acceptance criterion 8.
**Suggested fix**: You can track manual repair retry budgets independently from generation turns, or reset the counter to three when an error banner displays outside active generation.

## Minor
### 🟡 Broad substring check triggers false positive diagnostics, `packages/sandbox/src/runner.ts:155`
**Problem**: The runner inspects output logs by checking if the text includes the lowercase word `error`.
**Why it matters**: Harmless output containing the word error, such as package scripts, file names like `PreviewErrorBanner`, or informational logs, can trigger diagnostic errors and fail verification.
**Suggested fix**: You can refine the check with word boundary patterns or match specific compiler diagnostic prefixes.

### 🟡 Non ASCII text causes byte corruption in SHA256 helper, `packages/sandbox/src/diagnostics.ts:38`
**Problem**: The `pureSha256` function reads character codes using `charCodeAt` and shifts them into 32 bit words. When character values exceed 255, the bit shift overflows into adjacent byte positions.
**Why it matters**: Error messages containing smart quotes, em dashes, or foreign characters produce distorted word buffers during fingerprint calculation.
**Suggested fix**: You can encode text to UTF8 bytes with `TextEncoder` before packing words into the hash buffer.

### 🟡 Recomputing prime constants on every hash call, `packages/sandbox/src/diagnostics.ts:23`
**Problem**: `pureSha256` runs loops to discover primes and compute fractional square and cube roots on every invocation.
**Why it matters**: Recomputing these constants on every fingerprint calculation creates unnecessary overhead.
**Suggested fix**: You can move the initial hash state and round constants into top level static arrays outside the function.

### 🟡 In memory rate limiter map leak, `apps/web/src/app/api/projects/[id]/repair/route.ts:17`
**Problem**: `projectRepairTimestamps` stores request timestamps in a module level map keyed by project identifier. Keys for completed projects are never removed.
**Why it matters**: In long running Node processes, this map will accumulate entries over time.
**Suggested fix**: You can delete the project key from the map when its timestamp list becomes empty.

### 🟡 Cross origin frame inspection throws silent SecurityError, `apps/web/src/app/sandbox/runner/page.tsx:46`
**Problem**: The runner helper `hasErrorOverlay` queries `iframe.contentDocument` directly. Because WebContainer runs on a separate origin, browser security blocks this access and triggers a cross origin error caught by the empty catch block.
**Why it matters**: The helper always returns false, making error overlay detection rely entirely on post message bridge events.
**Suggested fix**: You can rely on post message events from the template client or document the cross origin limitation clearly in comments.
