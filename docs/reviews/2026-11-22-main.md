# Review, main, 2026-11-22

**Reviewed by**: Senior Review Agent (author on main model)
**Scope**: 36 files, uncommitted
**Verdict**: Blocked

## Summary
The change introduces an extensive design system foundation, Radix UI accessible component primitives, dark-mode-first studio theming with Geist fonts, a resizable workbench layout, and an isolated preview frame with postMessage event bridging. While the aesthetic finish, accessibility primitives, and unit test suite are remarkably high quality, critical issues were identified in layout persistence (collapsing chat causes permanent schema validation failures on reload), drag shield handling (mouse releases off the separator trap an invisible overlay over the preview), security isolation (defaulting the sandbox runner to same-origin path), duplicate DOM and iframe mounting between responsive viewports, and unwired device mode persistence in the builder page.

## Blockers
### 🔴 Layout reset on reload when chat panel is collapsed, `apps/web/src/hooks/useWorkspaceLayout.ts:8-12`
**Problem**: When the chat panel is collapsed via `toggleChatCollapse`, `chatPanelSize` is set to `0` and `previewPanelSize` is set to `100` before saving to `localStorage`. On page reload or hydration, `readStoredLayout()` runs `workspaceLayoutSchema.safeParse(parsed)`. The schema enforces `chatPanelSize: z.number().min(15).max(50)` and `previewPanelSize: z.number().min(50).max(85)`. Because `0 < 15` and `100 > 85`, `safeParse` fails every time. `readStoredLayout()` logs a warning, falls back to `DEFAULT_LAYOUT_STATE`, and resets the workspace to uncollapsed (30%/70%). Furthermore, `normalizeLayoutSizes(0)` clamps the size with `Math.max(15, 0) = 15`.
**Why it matters**: A collapsed workspace layout cannot survive a page refresh; user preferences are completely discarded on reload whenever chat is collapsed, violating acceptance criterion AC-4.
**Suggested fix**: Update `workspaceLayoutSchema` to permit `0` for `chatPanelSize` and `100` for `previewPanelSize` (e.g. `z.number().min(0).max(50)` or a schema union matching `isChatCollapsed: true`), and ensure `normalizeLayoutSizes` or `readStoredLayout` does not clamp `chatPanelSize: 0` to 15 when collapsed.

## Major
### 🟠 Stuck drag overlay shielding preview when mouse is released off separator, `apps/web/src/components/layout/BuilderWorkbench.tsx:98-121`
**Problem**: The drag state handlers `onMouseDown={() => setIsDragging(true)}` and `onMouseUp={() => setIsDragging(false)}` are attached directly to the thin (6px) `<Separator>` element. During normal panel dragging, the pointer moves away from the 6px separator. When the mouse button is released outside the separator bounds, the `mouseup` event fires on document/overlay elements rather than `<Separator>`, leaving `isDragging` permanently `true`.
**Why it matters**: While `isDragging` remains `true`, an invisible full-size overlay (`<div className="absolute inset-0 z-50 cursor-col-resize bg-transparent" />`) covers the entire preview panel. The user can no longer interact with, click, or test the live preview application, and the cursor remains permanently stuck as `col-resize`.
**Suggested fix**: Manage drag state using global window/document pointerup and mouseup event listeners (attaching on pointerdown and removing on release), or use `react-resizable-panels`'s built-in dragging callbacks.

### 🟠 Security boundary bypassed by defaulting preview runner to same-origin path, `apps/web/src/app/page.tsx:35`
**Problem**: In `apps/web/src/app/page.tsx:35`, `sandboxUrl` defaults to `"/sandbox"` when `NEXT_PUBLIC_SANDBOX_URL` is unset, running the iframe on `http://localhost:3000/sandbox` (same origin as the host). Spec 0003 (AC-6, Security model, and configuration line 117) explicitly mandates defaulting to `http://127.0.0.1:3000/sandbox` in development to ensure separate origin isolation. Furthermore, `usePreviewBridge.ts:65` validates `event.origin !== targetOrigin` but never verifies `event.source === iframeRef.current?.contentWindow`.
**Why it matters**: Running an iframe with `sandbox="allow-scripts allow-same-origin"` on the same origin as the host permits scripts inside the untrusted preview iframe to access parent window `localStorage`, cookies, and DOM. Furthermore, omitting `event.source` checks allows any popup or window on `targetOrigin` to spoof bridge messages.
**Suggested fix**: Set the default `sandboxUrl` fallback to `http://127.0.0.1:3000/sandbox` in development as required by the specification. In `usePreviewBridge.ts`, verify `if (iframeRef.current && event.source !== iframeRef.current.contentWindow) return;`.

### 🟠 Duplicate DOM mounting of workbench, iframes, and forms on mobile and desktop, `apps/web/src/components/layout/BuilderWorkbench.tsx:51-163`
**Problem**: `BuilderWorkbench` renders both the desktop resizable layout (`<div className="hidden h-full w-full md:flex">`) and the mobile tab layout (`<div className="flex h-full w-full flex-col md:hidden">`) simultaneously in the React DOM.
**Why it matters**: Both branches remain mounted in React. When `mobileTab === "preview"` (or on mobile screens), two live sandbox iframes and two chat forms are mounted in the DOM. This doubles CPU and memory usage, triggers duplicate network requests to the sandbox runner, creates duplicate DOM form controls with identical labels, and causes `iframeRef.current` to be overwritten by whichever iframe mounts last.
**Suggested fix**: Conditionally render the desktop vs mobile trees using a responsive media query hook (e.g. `useMediaQuery("(min-width: 768px)")`) or restructure the workbench so `chatContent` and `previewContent` have a single shared DOM mount styled responsively.

### 🟠 Preview device mode persistence disconnected in BuilderPage, `apps/web/src/app/page.tsx:20, 160-176`
**Problem**: In `apps/web/src/app/page.tsx:20`, device mode is managed in an isolated local `useState<DeviceMode>("desktop")` instead of consuming `layout.previewDevice` and `setPreviewDevice` from `useWorkspaceLayout`.
**Why it matters**: Acceptance criterion AC-4 requires `previewDevice` to persist in `localStorage` (`sparkweb:layout:v1`). Because `page.tsx` never calls `setPreviewDevice` or reads stored device preferences from `useWorkspaceLayout`, changing device modes in the toolbar does not persist across page reloads, always resetting back to `"desktop"`.
**Suggested fix**: Consume `layout.previewDevice` and `setPreviewDevice` from `useWorkspaceLayout` in `BuilderPage` (or share layout state through a shared layout context).

## Minor
### 🟡 Connection state not reset on iframe reload, `apps/web/src/app/page.tsx:73-76`
**Problem**: Acceptance criterion AC-7 specifies "connection state reset on iframe reload". When `handleReload` runs in `page.tsx`, it increments `iframeKey` to remount the iframe but does not call `resetConnection()` from `usePreviewBridge`.
**Why it matters**: `isConnected` remains `true` while the new iframe document is loading, causing outgoing messages sent during reload to bypass the handshake buffer and be dispatched prematurely before `PREVIEW_READY`.
**Suggested fix**: Invoke `resetConnection()` inside `handleReload` or when the iframe ref remounts.

### 🟡 Window message event listener reattached on every render, `apps/web/src/app/page.tsx:37-45`
**Problem**: In `apps/web/src/app/page.tsx`, `onMessage` is passed as an inline anonymous function. In `usePreviewBridge.ts:98`, `useEffect` depends on `onMessage`.
**Why it matters**: Every character typed into the prompt textarea triggers a re-render of `BuilderPage`, creating a new `onMessage` function and causing `usePreviewBridge` to remove and re-attach the `window` message listener on every keystroke.
**Suggested fix**: Store `onMessage` in a ref inside `usePreviewBridge` (`const onMessageRef = useRef(onMessage); onMessageRef.current = onMessage;`) so listener attachment does not depend on callback function identity.

### 🟡 Radix Slot error when Button combines asChild with isLoading, `apps/web/src/components/ui/button.tsx:45-77`
**Problem**: When `asChild` is `true`, `Comp` is `Slot`. If `isLoading` is also `true`, `<Comp>` renders both the spinner `<svg>` and `{children}` as siblings.
**Why it matters**: Radix `@radix-ui/react-slot` throws an invariant runtime error (`React.Children.only expected to receive a single React element child`) if `Slot` receives multiple children.
**Suggested fix**: Suppress the sibling spinner when `asChild` is true, or wrap the combined spinner and children in a single container element before passing to `Slot`.

### 🟡 Inaccessible interactive suggestion badges in Prompt Assistant, `apps/web/src/app/page.tsx:118-134`
**Problem**: The quick-suggestion badges (`+ Add user table`, `+ Sales analytics chart`) have `onClick` handlers but are rendered as non-interactive `<div>` elements without `role="button"`, `tabIndex={0}`, or keyboard event handlers.
**Why it matters**: Violates WCAG 2.1 AA keyboard accessibility requirements; users navigating with keyboard cannot tab to or activate these suggestion prompts.
**Suggested fix**: Render interactive suggestions as `<button>` elements (e.g. using `Button` with variant `outline` or adding keyboard handlers and button semantics to `Badge`).
