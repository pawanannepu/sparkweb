## Summary

Slice 6 implements one click publishing and isolated live hosting across `@spark/shared`, `@spark/db`, `@spark/edge-router`, and `apps/web`, introducing the `project_domains` schema and migration, an isolated Vite build runner, `LocalFsArtifactStore` and `S3ArtifactStore`, `LocalDevHostingAdapter` and `CloudflareSaasHostingAdapter`, Next.js subdomain proxy routing with `/live/[subdomain]/[[...path]]`, deployment and domain verification APIs, and the `PublishPopover` and `CustomDomainDialog` UI. Biome linting (`248` files), workspace TypeScript checks (`@spark/shared`, `@spark/db`, `@spark/edge-router`, `@spark/sandbox`, and `web`), and Vitest (`72` files, `435` tests) all pass, with clean PGlite transactional tests and well structured UI accessibility. However, merge is blocked by a post activation failure handling bug and stale domain capture in `executeDeploymentBuild` that can corrupt active deployment state and resurrect deleted host routes, alongside major issues covering concurrent build races and stuck build deadlocks, incomplete `/live` origin isolation and `proxy.ts` crash risks, missing `seed.sql` emission and path normalization bypasses in `strip-builder.ts`, cross-tenant rate limit exhaustion in domain verification, stale `deploymentUrl` after custom domain edits, and untested build timeout and external adapter error paths.

## Blockers

### 🔴 Post-activation route sync failure corrupts active deployment state and uses stale pre-build domain metadata, `apps/web/src/lib/publishing/deploy-service.ts:154`
**Problem**: In `executeDeploymentBuild` (`apps/web/src/lib/publishing/deploy-service.ts:152-178`), `activateDeployment` runs at line 154 and commits a PostgreSQL transaction that retires any prior active deployment, marks the new deployment `active`, and sets `projects.activeDeploymentId`. Only after that commit does line 169 call `syncRoutesForDomain(hostingAdapter, params.domain, routeRecord)`. If `syncRoutesForDomain` throws (for example, a transient Cloudflare KV error or rate limit), the `catch` block (`deploy-service.ts:170-177`) calls `failDeployment(database, ...)` with `buildLogs: message` and `buildDurationMs: 0`. In addition, `params.domain` is loaded once before the build starts (`apps/web/src/app/api/projects/[id]/deployments/route.ts:174-186`), even though `npm install` and `vite build` can take up to 120 seconds.
**Why it matters**: Any transient KV failure after `activateDeployment` overwrites the newly active deployment to `status = 'failed'`, erases the real build logs and duration, leaves `projects.activeDeploymentId` pointing to a `failed` row while the prior release is already `retired`, and leaves edge KV pointing to the old release (or causes `resolveLiveDeploymentBySubdomain` in local dev to return `404`). Furthermore, if the creator renames their subdomain or changes/verifies a custom domain while a build is running, `executeDeploymentBuild` pushes routes to the stale pre-build subdomain or removed custom domain and persists an outdated `deploymentUrl`.
**Suggested fix**: Track whether `activateDeployment` has committed (`activated`) so post-activation route sync errors never downgrade an `active` deployment to `failed` (instead retry KV sync with backoff or surface a sync warning while preserving the active record, and if an upload error occurs before activation, preserve `buildResult.buildLogs` and `buildResult.durationMs` in `failDeployment`). Also re-read the current `project_domains` row inside `activateDeployment` to update `subdomain`, `customDomain`, and `deploymentUrl` atomically, and return the fresh `domain` so `syncRoutesForDomain` always writes routes for the current domains.

## Major

### 🟠 Concurrent build lock race and permanent stuck-build deadlock on server restart, `packages/db/src/publishing-queries.ts:288`
**Problem**: `createDeployment` (`packages/db/src/publishing-queries.ts:288-301`), `rollbackToDeployment` (`packages/db/src/publishing-queries.ts:515-528`), and `unpublishProject` (`packages/db/src/publishing-queries.ts:604-617`) check for concurrent builds using a plain `SELECT` on `deployments` (`WHERE status IN ('queued', 'building')`) under PostgreSQL default `READ COMMITTED` isolation without locking the parent `projects` row (`FOR UPDATE`) and without a partial unique index on `deployments` (`packages/db/src/schema/deployments.ts:43-48`) covering `status IN ('queued', 'building')`. Likewise, `generateAvailableSubdomain` (`packages/db/src/publishing-queries.ts:98-129`) checks availability with a `SELECT` before inserting, which can fail with a `23505` unique violation under concurrent first publishes of two projects sharing a slug. Separately, `POST /api/projects/[id]/deployments` (`apps/web/src/app/api/projects/[id]/deployments/route.ts:180`) launches `void executeDeploymentBuild(...)` detached from the response lifecycle with no stale-build TTL recovery (unlike `checkActiveGeneration` in `packages/db/src/queries.ts:494`).
**Why it matters**: Simultaneous publish clicks pass the `SELECT` guard concurrently and spawn parallel `npm install` and `vite build` processes, violating AC-2. Worse, if the Node process restarts or a serverless worker suspends after returning `202` while a build is `queued` or `building`, the deployment remains stuck forever and permanently blocks all future publishes, rollbacks, and unpublishes with `409 Conflict`.
**Suggested fix**: Add a partial unique index `deployments_one_in_progress_per_project_idx` on `deployments(project_id)` where `status IN ('queued', 'building')` (mapping unique violations to `ConflictError`), lock the owning `projects` row (`FOR UPDATE`) in deployment state transitions, retry on `23505` subdomain collisions in `generateAvailableSubdomain`, use Next.js `after()` (or a durable job queue) for build execution, and automatically expire stale `queued`/`building` deployments older than a safe TTL (for example 5 minutes) into `failed` so projects cannot permanently deadlock.

### 🟠 Incomplete builder-origin isolation check in `/live` handler and unhandled URL crash in `proxy.ts`, `apps/web/src/app/live/[subdomain]/[[...path]]/route.ts:34`
**Problem**: In `apps/web/src/app/live/[subdomain]/[[...path]]/route.ts:34-42`, the origin isolation guard only redirects requests whose `Host` header is `localhost` or `127.0.0.1`. It does not reject IPv6 loopback (`[::1]`) or production builder hostnames (such as `sparkweb.dev` or `app.sparkapps.dev`). If reached directly without `proxy.ts` redirecting first, lines 47-65 fall back to `getPlatformHostnames(normalizedSubdomain)` and `resolveLiveDeploymentBySubdomain` and serve the published bundle directly on the builder host. Meanwhile, in `apps/web/src/proxy.ts:47-58`, `targetSubdomain` extracted from `/live/<targetSubdomain>` is interpolated unvalidated into `new URL(..., isolatedOrigin)`, which throws an unhandled `TypeError: Invalid URL` (`500`) on encoded characters like `/live/foo%23bar` and permits `@` userinfo injection (for example `http://user@sub.localhost:3000/`) in redirect targets.
**Why it matters**: Defense in depth for AC-8 fails on non-localhost builder origins and `[::1]`, risking execution of untrusted generated JavaScript on the `sparkweb` origin with access to builder session cookies and origin storage, while malformed `/live/` paths crash Next.js request handling in `proxy.ts` with `500`.
**Suggested fix**: Validate `targetSubdomain` (and `subdomain` in `route.ts`) strictly against `^[a-z0-9](?:[a-z0-9-]{1,61}[a-z0-9])$`, returning `404` on invalid segments in `proxy.ts` and `route.ts` instead of constructing unvalidated `URL` strings. In `route.ts`, allow serving assets only when the request `Host` matches an isolated live domain (a `*.localhost` host, a non-reserved `*.${PLATFORM_DOMAIN}` subdomain, or a verified custom domain) and redirect or return `404` for all builder hosts including `[::1]`.

### 🟠 Production Vite builds drop root `seed.sql` and allow backslash/dot-slash paths to bypass script stripping, `apps/web/src/lib/publishing/strip-builder.ts:90`
**Problem**: Snapshots store exported database seeds at root `"seed.sql"` (`apps/web/src/app/api/projects/[id]/database/seed/route.ts:83`), and generated apps fetch them at runtime via `fetch("/seed.sql")` (`packages/sandbox/src/template.ts:993`). Vite dev mode serves project root files at `/seed.sql`, whereas `vite build` only copies files inside `public/` into `dist/`. `prepareProductionFiles` (`apps/web/src/lib/publishing/strip-builder.ts:90-125`) never copies `"seed.sql"` into `"public/seed.sql"`, so `fetch("/seed.sql")` on published sites hits the SPA fallback (`index.html`) and silently skips seeding. In addition, line 95 (`rawPath.replace(/^\/+/, "")`) does not strip leading `./` or normalize `\` separators to `/`: paths like `src\spark-inspector-client.ts` or `plugins\spark-inspector.js` fail to match `BUILDER_ONLY_FILES` in `prepareProductionFiles` and are then normalized and written to disk by `resolveSafeTempPath` (`apps/web/src/lib/publishing/build-runner.ts:14`), while `./src/main.tsx` fails `resolveSafeTempPath` because it contains a `.` segment.
**Why it matters**: Every live application published with saved `seed.sql` data launches with empty database tables, and snapshots using `./` or `\` path prefixes either crash the build runner or retain builder-only inspector/bridge files inside the production bundle.
**Suggested fix**: Normalize `rawPath` in `prepareProductionFiles` using `.replace(/\\/g, "/").replace(/^(?:\.\/|\/)+/, "")` so it matches `resolveSafeTempPath` and `isSourceFilePath`, and when `seed.sql` is present in the snapshot without `public/seed.sql`, emit it at `public/seed.sql` in the returned production file map so `vite build` copies it into `dist/seed.sql`.

### 🟠 Domain verification consumes rate limit before ownership check and ignores routing/DCV validation details, `apps/web/src/app/api/projects/[id]/domain/verify/route.ts:22`
**Problem**: `POST /api/projects/[id]/domain/verify` (`apps/web/src/app/api/projects/[id]/domain/verify/route.ts:22-36`) calls `checkVerifyRateLimit(projectId)` before `getProjectDomain(db, { projectId, userId: user.id })` checks project ownership. Second, lines 85-96 call `adapter.putRoute(updatedDomain.customDomain, ...)` whenever `sslStatus === "active"` without checking `dnsResult.routingVerified` (so `LocalDevHostingAdapter`, which always returns `sslStatus: "active"`, activates routing even when CNAME/A DNS lookup fails). Third, `CloudflareSaasHostingAdapter.syncCustomHostname` (`apps/web/src/lib/publishing/hosting-adapter.ts:239-243`) creates custom hostnames with `ssl: { method: "txt", type: "dv" }`, which causes Cloudflare to require its own DCV TXT record (`ssl.validation_records` in the API response) in addition to `_sparkweb-verify.<domain>`, yet `CustomHostnameRegistration` discards `validation_records` and never surfaces them to the creator. Also note that if a previously created `providerHostnameId` was deleted in Cloudflare (`404`), `getCustomHostnameStatus` (`route.ts:68`) fails instead of re-syncing via `syncCustomHostname`.
**Why it matters**: Any authenticated user can send five POST requests to another tenant's project ID, get `403`, and lock out the real owner's DNS verification (`429`). In production, `method: "txt"` custom hostnames without surfaced Cloudflare `validation_records` can remain stuck in `sslStatus: "pending"` even after `_sparkweb-verify` and CNAME/A records are configured.
**Suggested fix**: Authenticate and verify project ownership via `getProjectDomain` before calling `checkVerifyRateLimit`, require `dnsResult.routingVerified` (or explicit local-only dev override) before publishing the custom domain route, and either switch Cloudflare custom hostname SSL validation to `method: "http"` (which validates automatically via the customer CNAME/A record) or include Cloudflare `ssl.validation_records` in `CustomHostnameRegistration` and `dnsInstructions`, falling back to `syncCustomHostname` if `getCustomHostnameStatus` reports a missing hostname (`404`).

### 🟠 Replacing a custom domain leaves stale `deploymentUrl` on the active deployment and allows partial PATCH commits, `packages/db/src/publishing-queries.ts:773`
**Problem**: When `configureProjectCustomDomain` (`packages/db/src/publishing-queries.ts:773-798`) replaces an existing custom domain, it resets `verificationStatus` to `"pending"` and `sslStatus` to `"unconfigured"`, and `PATCH /api/projects/[id]/domain` (`apps/web/src/app/api/projects/[id]/domain/route.ts:104-109`) deletes the old custom domain route from `HostingAdapter`. However, unlike `clearProjectCustomDomain` and `updateCustomDomainVerificationState`, `configureProjectCustomDomain` never updates `customDomain` or `deploymentUrl` on the project's active deployment row. Because `PublishPopover` (`apps/web/src/components/publishing/PublishPopover.tsx:72`) reads `activeDeployment.deploymentUrl`, the UI continues displaying and linking to the deleted old `https://old.example.com` (now returning `404`) instead of reverting to the platform subdomain URL. Additionally, `PATCH /api/projects/[id]/domain` (`domain/route.ts:63-114`) commits `updateProjectSubdomain` and mutates live routes before validating `customDomain` at line 92, causing partial DB and KV updates when a two-field payload has an invalid `customDomain`, and lines 71-88 delete the old subdomain route before writing the new one.
**Why it matters**: Replacing a live custom domain breaks the live URL link shown to creators in the builder until verification of the new domain completes, while invalid dual-field `PATCH` requests silently mutate subdomains before failing with `422`.
**Suggested fix**: Update `activeDeployment.customDomain = null` and recompute `activeDeployment.deploymentUrl` inside `configureProjectCustomDomain` (mirroring `clearProjectCustomDomain`), validate all incoming `subdomain` and `customDomain` inputs before opening DB/KV mutations in `PATCH /api/projects/[id]/domain`, and on subdomain renames write the new `HostingAdapter` routes before removing the old subdomain routes.

## Minor

### 🟡 Unvalidated pagination `cursor` causes `500` and redundant domain query risks orphaned queued deployments, `apps/web/src/app/api/projects/[id]/deployments/route.ts:47`
**Problem**: `GET /api/projects/[id]/deployments` (`apps/web/src/app/api/projects/[id]/deployments/route.ts:47`) forwards arbitrary `?cursor=` strings directly into `listDeployments` (`packages/db/src/publishing-queries.ts:380-393`), where `eq(deployments.id, params.cursor)` triggers a PostgreSQL `invalid input syntax for type uuid` `500` error instead of `400`. In `POST /api/projects/[id]/deployments` (`deployments/route.ts:168-177`), a second query `getProjectDomain` runs after `createDeployment` already inserted a `'queued'` row; if that lookup returned `null`, returning `500` leaves the `'queued'` row permanently blocking future builds. Also, `createDeployment` (`publishing-queries.ts:316`) copies `domain.customDomain` onto `deployments.customDomain` even when `verificationStatus !== "verified"`, unlike `updateCustomDomainVerificationState` (`line 864`).
**Why it matters**: Malformed client cursors produce noisy `500` server errors, and `deployments.customDomain` records unverified domains inconsistently across code paths.
**Suggested fix**: Validate `cursor` with `isValidUuid` (returning `400` on invalid UUIDs), return `{ deployment, domain }` directly from `createDeployment` to eliminate the extra `getProjectDomain` round trip, and set `deployments.customDomain` only when `domain.verificationStatus === "verified"`.

### 🟡 S3 `deletePrefix` scales sequentially with unescaped XML keys and external HTTP calls lack timeouts, `apps/web/src/lib/publishing/artifact-store.ts:297`
**Problem**: `S3ArtifactStore.deletePrefix` (`apps/web/src/lib/publishing/artifact-store.ts:316-328`) parses `<Key>` elements with a regex without decoding XML entities (such as `&amp;`), does not trim leading slashes from `objKey` before formatting `/${this.bucket}/${objKey}`, and issues sequential single-object `DELETE` requests one by one inside the synchronous `DELETE /api/projects/[id]` handler. Neither `S3ArtifactStore` (`artifact-store.ts:249-328`) nor `CloudflareSaasHostingAdapter` (`hosting-adapter.ts:173-282`) sets `AbortSignal.timeout` on `fetch`, and `CloudflareSaasHostingAdapter` (`lines 246, 265`) calls `res.json()` unconditionally even if Cloudflare returns non-JSON error HTML (such as a 502 gateway page).
**Why it matters**: Deleting a project with many historical deployments can hang or time out `DELETE /api/projects/[id]` due to hundreds of sequential `DELETE` calls or stalled upstream requests before database deletion executes.
**Suggested fix**: Use S3 batch `DeleteObjects` (or bounded concurrent deletes) after XML-unescaping keys and trimming leading slashes, add `AbortSignal.timeout` to all S3 and Cloudflare `fetch` calls, and safely parse error bodies when `!res.ok` in `CloudflareSaasHostingAdapter`.

### 🟡 Build runner lacks `.npmrc`/`node_modules` write guards and stdout/stderr byte limits; `vite.config` regex is fragile, `apps/web/src/lib/publishing/build-runner.ts:76`
**Problem**: `runIsolatedViteBuild` (`apps/web/src/lib/publishing/build-runner.ts:144-154`) writes all `productionFiles` to temp disk without filtering `node_modules/` or `.npmrc`. A snapshot containing `.npmrc` or `node_modules/.bin/vite` (if constructed outside `snapshots/route.ts`) could influence `npm` registry settings or the `viteBin` binary executed at line 200. In addition, `runSanitizedCommand` (`build-runner.ts:76-91`) buffers unbounded stdout/stderr in memory and stores it verbatim in `deployments.buildLogs`. Separately, `stripViteConfigContent` (`apps/web/src/lib/publishing/strip-builder.ts:41-71`) matches `worker: {[^}]*}` and `defineConfig({`, which fails if `worker` contains nested braces or `defineConfig` uses a callback `({ mode }) => ({ ... })`, and `BUILDER_IMPORT_LINE_PATTERN` only runs on `src/main.*`.
**Why it matters**: Chatty or failing builds can consume excessive memory and bloat PostgreSQL `deployments` rows, snapshot-provided `.npmrc` files weaken build isolation, and non-trivial `vite.config.ts` syntax fails config normalization.
**Suggested fix**: Reject or skip `node_modules/`, `.npmrc`, `dist/`, and `.vite/` inside `prepareProductionFiles` / `runIsolatedViteBuild`, cap captured `buildLogs` (for example 256 KB with truncation notice), and parse/transform `vite.config.ts` and builder imports via AST (such as `recast`/`@babel/parser`, already in `apps/web/package.json`) or guard nested braces.

### 🟡 Stale fallback DNS records in `CustomDomainDialog`, mobile popover overflow, and polling interval churn in `usePublishing`, `apps/web/src/components/publishing/CustomDomainDialog.tsx:92`
**Problem**:

When a page reloads with a configured custom domain, `usePublishing` has `dnsInstructions === null` because `GET /api/projects/[id]/deployments` only returns `domain`. `CustomDomainDialog` (`apps/web/src/components/publishing/CustomDomainDialog.tsx:92-105`) then falls back to hardcoded `"192.0.2.1"` and `"edge.sparkapps.dev"` instead of using server-configured `PLATFORM_APEX_IP` and `PLATFORM_CNAME_TARGET`.

In `usePublishing` (`apps/web/src/hooks/usePublishing.ts:63-90`), putting the `inProgressDeployment` object reference in the polling `useEffect` dependency array tears down and recreates `setInterval` after every poll update (`setDeployments`), and `fetchDeployments` (`usePublishing.ts:38-52`) silently ignores non-OK responses and network failures.

### 🟡 Ad-hoc `process.env` reads, silent driver fallbacks, and divergent `PLATFORM_DOMAIN` defaults, `apps/web/src/lib/publishing/deploy-service.ts:20`
**Problem**: In violation of the `AGENTS.md` rule to validate env vars at startup with Zod, `deploy-service.ts`, `dns-verify.ts`, `publishing-queries.ts`, and `proxy.ts` read publishing env vars ad-hoc via `process.env`. Worse, `getArtifactStore` (`deploy-service.ts:23`) and `getHostingAdapter` (`deploy-service.ts:52`) silently fall back to `"local"` for any driver value other than `"s3"` or `"cloudflare"` (so typos like `HOSTING_DRIVER=Cloudflare` or `ARTIFACT_STORAGE_DRIVER=r2` silently store bundles on local temp disk). Furthermore, `PLATFORM_DOMAIN` defaults to `"localhost:3000"` in `publishing-queries.ts:76` when `HOSTING_DRIVER !== "cloudflare"`, whereas `deploy-service.ts:79`, `dns-verify.ts:67`, and `proxy.ts:4` default it to `"sparkapps.dev"`, and `getPlatformHostnames` (`deploy-service.ts:84`) writes `.localhost` keys even when `HOSTING_DRIVER=cloudflare`.
**Why it matters**: Driver misconfiguration fails silently instead of failing fast at startup, and inconsistent `PLATFORM_DOMAIN` defaults pollute Cloudflare KV with `.localhost` entries in production and `.sparkapps.dev` entries in local dev.
**Suggested fix**: Centralize publishing configuration behind a Zod-validated config helper (rejecting unknown `ARTIFACT_STORAGE_DRIVER` or `HOSTING_DRIVER` values and enforcing required S3/Cloudflare keys when enabled), unify the default `PLATFORM_DOMAIN` logic across packages, and emit `.localhost` hostnames only in local mode or when `platformDomain` is `localhost`.

- **Clean layered architecture**: Clear separation across `@spark/shared` contracts, `@spark/db` `project_domains` and `deployments` schema/queries, `ArtifactStore` and `HostingAdapter` interfaces, `@spark/edge-router`, API routes, and React hooks/components with zero `any` types and full Biome/TypeScript compliance.
