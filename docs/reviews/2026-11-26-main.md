## Summary
Slice 5 delivers the managed database viewer and client data tools across `packages/shared`, `packages/db`, `packages/sandbox`, `apps/web`, and `e2e/`, adding `project_queries`, REST CRUD and `seed.sql` snapshot endpoints, postMessage PGlite bridge contracts, a TanStack Table v8 record browser, a CodeMirror 6 SQL Console, and continuous `PreviewFrame` mounting. Type checking (`pnpm check-types`), linting (`pnpm lint`, 197 files), and unit tests (`pnpm test`, 52 files and 344 tests) all pass, and the Drizzle migration and PostgreSQL queries are well structured and thoroughly tested. However, merge is blocked by missing origin and source validation on the two hop sandbox postMessage bridge, alongside five major issues: an engine level `SET TRANSACTION READ ONLY` bypass via multi statement SQL, an unused 800 line `db-bridge.ts` module tested in place of the untyped inline runtime in `template.ts`, `seed.sql` and cell editing failures on mixed case identifiers, `GENERATED ALWAYS AS IDENTITY`, JSON scalar strings, and PostgreSQL arrays, duplicate React keys and unhandled rejections in `SqlConsole`, and row loading race conditions with duplicate bridge refreshes.

## Blockers
### 🔴 Missing origin and source validation on the sandbox postMessage bridge, `apps/web/src/app/sandbox/runner/page.tsx:92`
**Problem**: In `apps/web/src/app/sandbox/runner/page.tsx:92-104`, `handleMessage` checks `event.source === window.parent` for parent commands, but never validates `event.origin` against the expected host origin, and relays responses with wildcard target origin `"*"` in `postToHost` (`apps/web/src/app/sandbox/runner/page.tsx:43`) and lines `213` and `255`. Worse, in the `else` branch (`apps/web/src/app/sandbox/runner/page.tsx:216-258`), any message with `protocol: "sparkweb:bridge:v1"` from any window or frame is forwarded to `window.parent` as `DB_READY_EVENT`, `DB_INTROSPECT_RESPONSE`, `DB_QUERY_RESPONSE`, `DB_MUTATE_RESPONSE`, `DB_EXPORT_SEED_RESPONSE`, or `PREVIEW_ERROR` without verifying `event.source === appIframe.contentWindow` or `event.origin` against `previewUrlRef.current`. Inside the app iframe (`packages/sandbox/src/template.ts:887-908`), the `spark-db-bridge.ts` listener performs no `event.source` or `event.origin` check before running arbitrary `DB_QUERY_REQUEST` SQL or `DB_MUTATE_REQUEST` writes against PGlite.
**Why it matters**: `PreviewFrame` (`apps/web/src/components/layout/PreviewFrame.tsx:97`) grants `allow-popups` and `allow-same-origin`. Because `usePreviewBridge` (`apps/web/src/hooks/usePreviewBridge.ts:102`) trusts everything relayed from `/sandbox/runner`, any popup or unauthorized frame can spoof database responses or errors up to the host, send SQL queries or mutations straight into PGlite inside the app frame, or receive database contents posted with `"*"`. This violates the origin validation rule in the security model of `docs/specs/0008-managed-database-viewer-and-client-data-tools/index.md:122`.
**Suggested fix**: In `apps/web/src/app/sandbox/runner/page.tsx`, verify `event.origin === window.location.origin` on parent commands, compute the expected inner app origin from `previewUrlRef.current`, verify both `event.source === appIframe.contentWindow` and `event.origin === expectedAppOrigin` before relaying inner frame events upstream, and pass explicit target origins instead of `"*"` to `postMessage`. In `packages/sandbox/src/template.ts` (`src/spark-db-bridge.ts`), verify `event.source === window.parent` (and expected runner origin when available) before handling `DB_*` requests.

## Major
### 🟠 Engine level read only transaction lock bypassed by multi statement SQL, `packages/sandbox/src/template.ts:675`
**Problem**: In both `packages/sandbox/src/template.ts:675-685` (`handleQuery`) and `packages/sandbox/src/db-bridge.ts:342-371` (`executePgliteQuery`), when `readOnly` is `true`, user SQL is wrapped in `BEGIN`, `SET TRANSACTION READ ONLY`, multi statement `db.exec(trimmed)`, and `COMMIT`. Because `db.exec(trimmed)` allows multiple statements, passing `COMMIT; INSERT INTO ...;` or `SET TRANSACTION READ WRITE; DROP TABLE ...;` exits or alters the read only transaction and executes writes or DDL (verified directly against PGlite 0.5.17). In addition, `apps/web/src/components/database/SqlConsole.tsx:132` skips `assessDestructiveSql` whenever `isStreamingLocked` is `true`, so destructive queries using `COMMIT;` do not even trigger a confirmation modal during streaming.
**Why it matters**: Active AI generation or repair passes (`STREAMING_LOCKED`, `AC 9` in `docs/specs/0008-managed-database-viewer-and-client-data-tools/index.md:31`) promise engine level `SET TRANSACTION READ ONLY` protection so database tables and schema remain immutable while streaming. A multi statement script silently mutates or drops tables underneath an active generation pass.
**Suggested fix**: Enforce read only mode with `SET default_transaction_read_only = on` (restoring `off` in a `finally` block) combined with rejecting transaction control and `SET` statements when `readOnly` is `true`, or execute single statements via `db.query` while still running `assessDestructiveSql` regardless of `isStreamingLocked`.

### 🟠 Duplicated `db-bridge.ts` tested instead of the untyped inline runtime in `template.ts`, `packages/sandbox/src/db-bridge.ts:46`
**Problem**: `packages/sandbox/src/db-bridge.ts` defines 802 lines of typed PGlite introspection, query, mutation, and `seed.sql` export logic, and `packages/sandbox/src/db-bridge.test.ts` tests those exports thoroughly. However, across the entire application, only `assessDestructiveSql` (`apps/web/src/components/database/SqlConsole.tsx:16`) and `MAX_SEED_SQL_BYTES` (`apps/web/src/app/api/projects/[id]/database/seed/route.ts:11`) are imported from `db-bridge.ts`. The sandbox runtime actually executes an inline duplicated copy inside string literals in `packages/sandbox/src/template.ts:490-1098` (`src/spark-db-bridge.ts` and `src/lib/db.ts`) written with `any` parameter types. Meanwhile, `e2e/database-viewer.spec.ts:53-152` mocks out `/sandbox/runner` completely, leaving the real `src/spark-db-bridge.ts` and `src/lib/db.ts` runtime code with zero unit or end to end test coverage.
**Why it matters**: Future fixes to `db-bridge.ts` will silently miss production unless copied manually into `template.ts`, and passing unit tests in `db-bridge.test.ts` create false confidence while `template.ts` drifts (for example, `template.ts` emits `DB_MUTATED_EVENT` while `db-bridge.ts` does not, and `template.ts` uses untyped `any`).
**Suggested fix**: Keep one canonical implementation and generate or embed the standalone WebContainer bridge source from tested module code (or extract its template source directly into `db-bridge.test.ts` and execute real `postMessage` and PGlite integration tests against `STARTER_TEMPLATE_FILES["src/spark-db-bridge.ts"]` and `STARTER_TEMPLATE_FILES["src/lib/db.ts"]`).

### 🟠 Seed export, replay, and CRUD fail on mixed case names, identity columns, JSON strings, and arrays, `packages/sandbox/src/template.ts:866`
**Problem**: Four data type and identifier bugs break PostgreSQL compatibility (each verified against PGlite 0.5.17):
1. `exportPgliteSeedSql` (`packages/sandbox/src/db-bridge.ts:723` and `packages/sandbox/src/template.ts:872`) emits `pg_get_serial_sequence('${escapedTable}', '${escapedCol}')` without double quoting mixed case table names inside the string literal. For a table named `"MyItems"`, PostgreSQL folds unquoted `'MyItems'` to `myitems` and throws `relation "myitems" does not exist`.
2. `exportPgliteSeedSql` (`packages/sandbox/src/db-bridge.ts:708` and `packages/sandbox/src/template.ts:861`) omits `OVERRIDING SYSTEM VALUE` on `INSERT` statements for `GENERATED ALWAYS AS IDENTITY` columns, which causes PostgreSQL to reject `seed.sql` replay with `cannot insert a non-DEFAULT value into column`.
3. `parseAndValidateCellValue` (`apps/web/src/components/database/value-utils.ts:82-89`) parses JSON inputs with `JSON.parse(raw)` and returns raw JavaScript values. When a user enters a valid JSON string such as `"hello"`, passing the unquoted string `"hello"` as a `$1` parameter to PGlite throws `invalid input syntax for type json`. Likewise, `toSqlLiteral` (`packages/sandbox/src/db-bridge.ts:79-85` and `packages/sandbox/src/template.ts:536-541`) only JSON serializes `typeof value === "object"`, exporting a `jsonb` string scalar `"hello"` as `'hello'` instead of `'"hello"'::jsonb`.
4. PostgreSQL array columns (such as `text[]` or `integer[]`) come back as JS arrays, so `toSqlLiteral` writes JSON array syntax `'["a","b"]'` and `value-utils.ts` sends `JSON.stringify` output on edits; both fail in PGlite with `malformed array literal`.
**Why it matters**: Any generated app that uses mixed case identifiers, `GENERATED ALWAYS AS IDENTITY`, array columns, or string values in `json`/`jsonb` columns will fail on visual editing (`AC 5`) or fail to boot from exported `seed.sql` (`AC 8`).
**Suggested fix**: Quote mixed case table names inside `pg_get_serial_sequence` (`'"MyItems"'`), emit `OVERRIDING SYSTEM VALUE` when any column uses `isIdentity` with `ALWAYS` generation (or inspect `attidentity`), pass `JSON.stringify(parsed)` when binding `json`/`jsonb` values and handle JSON primitives in `toSqlLiteral` whenever `columnType` includes `json`, and format JS arrays as PostgreSQL array literals (or explicit JSON text inputs) when `columnType` is an array type.

### 🟠 Duplicate React keys and unhandled rejections in `SqlConsole`, `apps/web/src/components/database/SqlConsole.tsx:420`
**Problem**: At `apps/web/src/components/database/SqlConsole.tsx:420-423`, query result rows are keyed by `key={JSON.stringify(row)}`. Whenever a query returns identical rows (such as `SELECT status FROM tasks;` or `SELECT 1 UNION ALL SELECT 1`), React receives duplicate keys and drops or misrenders rows. Furthermore, at `apps/web/src/components/database/SqlConsole.tsx:526-528` and `562`, the pin (`onUpdateSnippet`) and delete (`onDeleteSnippet`) icon buttons invoke async callbacks from `useDatabaseViewer` (which throw on non 2xx responses or network errors) without `try/catch` or `.catch()`.
**Why it matters**: Common aggregate or single column queries crash React key uniqueness and display corrupted tables, and any transient failure while pinning or deleting a saved query produces an unhandled promise rejection with zero user feedback.
**Suggested fix**: Key SQL result `<tr>` elements using a unique row index suffix (for example `${rowIdx}` since result rows are static per query execution) and wrap `onUpdateSnippet` and `onDeleteSnippet` clicks in `try/catch` with an error alert banner in the Saved Snippets sidebar.

### 🟠 Stale row race condition and redundant double refreshes in `useDatabaseViewer`, `apps/web/src/hooks/useDatabaseViewer.ts:121`
**Problem**: Three concurrency and refresh defects affect `useDatabaseViewer` (`apps/web/src/hooks/useDatabaseViewer.ts`):
1. `fetchTableRows` (`useDatabaseViewer.ts:121-165`) has no request sequence counter or active table guard, so switching tables or changing filters rapidly while an earlier `DB_QUERY_REQUEST` is in flight lets the older response or error overwrite the active table's `rows`, `totalCount`, and `rowsError`.
2. In `refreshActiveView` (`useDatabaseViewer.ts:206-217`), when `refreshSchema` detects that the selected table was dropped and calls `setSelectedTableName`, `setPage(1)`, `setSortColumn(undefined)`, and `setSearchQuery("")` (`useDatabaseViewer.ts:187-194`), line `212` immediately calls `fetchTableRows(target)` using the stale closure's old `page`, `sortColumn`, and `searchQuery` before React commits the state reset, and then the `useEffect` at lines `234-245` fires a second `fetchTableRows(target)`.
3. Because `spark-db-bridge.ts` emits `DB_MUTATED_EVENT` on every mutation and write query (`useDatabaseViewer.ts:286-288`), calling `refreshActiveView()` again in `executeMutation` (`useDatabaseViewer.ts:331-333`) and on every query result in `SqlConsole.tsx:109-111` (even pure `SELECT` statements) fires duplicate schema introspections (`SELECT COUNT(*)` per table) and duplicate row queries on every write and unnecessary full refreshes on read queries.
**Why it matters**: Rapid table switching can display rows from the wrong table, dropped tables send invalid old pagination/sort state, and every write doubles postMessage bridge traffic and catalog queries.
**Suggested fix**: Track an incrementing request sequence ref in `fetchTableRows` so stale responses and errors are ignored; pass explicit clean pagination/sort/search options when `refreshActiveView` switches fallback tables (or rely on the reactive `useEffect`); and avoid calling `refreshActiveView` twice when `DB_MUTATED_EVENT` already triggers revalidation (and only refresh after `SqlConsole` queries that actually mutate schema or rows).

## Minor
### 🟡 Stale modal errors in `DeleteRowDialog` and index keyed `InlineCellEditor`, `apps/web/src/components/database/DeleteRowDialog.tsx:30`
**Problem**: `DeleteRowDialog` (`apps/web/src/components/database/DeleteRowDialog.tsx:30-31`) remains mounted while closed and never resets its local `error` state when `isOpen` or `primaryKeyValues` changes, so a failed delete (such as a foreign key error) stays visible when the user cancels and opens Delete on a different row. Behind the modal, `DataGrid.tsx:682-684` also sets `mutationError`, which persists even after clicking `Refresh`. In `DataGrid.tsx:351-352`, `InlineCellEditor` is keyed by `${rowIdx}:${col.name}` rather than the row primary key, so if `DB_MUTATED_EVENT` inserts or deletes a row while editing row 0, saving can update a shifted row with stale `draftValue`.
**Why it matters**: Users see misleading errors on subsequent delete prompts and risk mutating the wrong record if background app activity changes row order during inline editing.
**Suggested fix**: Clear `error` inside `DeleteRowDialog` via `useEffect` whenever `isOpen` opens, keep delete errors inside the modal instead of duplicating `mutationError` on `DataGrid`, clear `mutationError` on `onRefresh`, and key `InlineCellEditor` by primary key values (closing the editor if that primary key disappears from `rows`).

### 🟡 Accessibility gaps in `AddRecordSheet`, workbench tabs, and snippet cards, `apps/web/src/components/database/AddRecordSheet.tsx:165`
**Problem**: In `AddRecordSheet.tsx:165-180`, every nullable column renders a checkbox whose label text is just `"NULL"` without naming the column. **Suggested fix**: Add `aria-label={`Set ${col.name} to NULL`}` on each checkbox, wire `id`, `aria-controls`, `role="tabpanel"`, `aria-labelledby`, and arrow key handling on the Preview/Database tabs, and replace `<p>`/`<pre>` inside `<button>` with `<span>` elements styled as blocks.

### 🟡 Schema prompt active during Inspect Mode and running `PREVIEW_BOOT` skips package install, `apps/web/src/app/page.tsx:731`
**Problem**: When `versionHistory.isInspectMode` is `true`, `BuilderPage` locks prompt submission in `ChatPanel` (`apps/web/src/app/page.tsx:516-523`), but leaves `onAskSparkSchema` and CRUD buttons enabled inside `DatabaseViewer` (`apps/web/src/app/page.tsx:731-769`).
